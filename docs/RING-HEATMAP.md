# 링 히트맵 (전체 사용자 링 중심 분포)

맵별로 "링이 어디로 끝나는가"를 축구 활동량 히트맵처럼 보여 주기 위한 설계 문서.

**상태:** 계획 (미구현). 링 데이터를 더 쌓은 뒤 §6 검증을 다시 돌리고 착수한다.
**작성일:** 2026-11-23
**관련:** [ARCHITECTURE.md](./ARCHITECTURE.md) (매치 V3) · [DB-OPTIMIZATION.md](./DB-OPTIMIZATION.md) · [GEP-BUGS.md](./GEP-BUGS.md) (next_ring 좌표 버그)
**코드:** `public/background/services/matchService.js` (`recordRing`, `finalizeRingRounds`), `src/types.ts` (`RingRound`), `src/components/MapVisualizer.tsx` (`buildRingCircles`), `src/utils/constants.ts` (맵 보정값)

## 1. 랜드마크 경계를 쓰지 않는 이유

랜드마크 단위 통계를 먼저 검토했으나 경계를 정확히 얻을 방법이 없다.

- **이름은 추출 가능.** 맵 팩(`mp_rr_<맵>.rpak`)의 존 데이터테이블에 `triggerName` / 현지화 키(`#DES_ZONE_*`) / `statsRef`(통계 그룹)가 있다. World's Edge 기준 47개. 한국어·영어 이름은 `localization_*.rpak`에서 같은 해시 함수로 조회된다 (`scripts/game-icons/rpak_guid.py`).
- **경계는 추출 불가.** World's Edge 맵 팩 4개(main, `(01)`, `client_perm`, `client_temp`)를 Oodle 해제 후 전수 검색한 결과:
  - 존 이름은 위 데이터테이블에만 존재. 트리거 엔티티·`classname`·해시된 존 이름 없음.
  - 클라이언트 엔티티 script_name은 화면·사일로 문뿐.
  - → 존 트리거 영역은 **서버 전용 데이터**로 판단. 실험 도구·메모: `D:\apex-extract\map-research\` (README.txt).
- **다른 소스도 없음.** GEP는 좌표만, LiveAPI는 5분할 `MapRegion`(커스텀 매치 전용)뿐.
- 손으로 그린 경계는 정확한 지표로 쓰기 어렵다 → 좌표 기반으로 간다.

## 2. 수집할 데이터

### 2.1 링 중심의 출처

- GEP `next_ring`의 x/y는 쓰레기 값 (GEP-BUGS). 반경만 유효.
- 중심은 수축이 끝난 시점의 `active_ring` 중심으로 채운다 (`finalizeRingRounds` → `centerSource: 'active_end'`).
- **수축이 끝난 라운드만 점이 된다.** 예고만 되고 끝나지 않은 라운드는 중심 없음.
- 사망 후 샘플도 `d = 1`로 기록된다. 관전 중 링까지 쓸지는 구현 시 결정.

### 2.2 라운드별 저장

- "마지막 링 하나"만 쓰면 3라운드 사망 경기와 최종까지 간 경기가 섞여 분포가 흐려진다. 또 최종 링만 쓰면 표본이 크게 준다.
- 경기마다 **3라운드 이후 확정된 모든 라운드**를 `(맵, 시즌, 라운드, x, y, 반경)`으로 집계하고, 화면에서 라운드를 고른다.
- **라운드 번호는 배열 순서가 아니라 반경으로 판정한다.** `next_ring`보다 `active_ring`이 먼저 오면 placeholder round 0이 생겨 번호가 밀린다. 맵별 라운드 반경은 고정이므로 `nextRingRadius`로 판정.

### 2.3 시즌 분리

- 시즌마다 링 로직·지형이 바뀌므로 **맵 + 시즌(또는 맵 빌드)** 단위로 따로 집계. World's Edge는 이미 s29/s30을 구분한다 (`resolveWorldsEdgeMapImage`).

## 3. 저장 구조

### 3.1 용량

| 방식 | 1경기당 | 하루 1만 경기 · 1년 |
|------|---------|---------------------|
| 라운드별 원본 점 (5개) | ~200B | ~0.7GB |
| 최종 링만 원본 | ~40B | ~0.15GB |
| **격자 집계** | 칸 카운트 +1 | **상한 고정** (맵 6 × 라운드 4 × 128² = 최대 ~40만 행, 실제로는 훨씬 적음) |

→ **격자 집계 테이블** 채택. 원본 점은 중복 판정용 지문만 보관하고 시즌 종료 후 삭제 가능.

### 3.2 테이블 (안)

- `ring_heatmap_cells` — `(map, season_id, round, cell_x, cell_y)` PK, `count`.
- `ring_match_fingerprints` — 중복 판정용. 맵 · 시즌 · 시작 시각 · 라운드별 중심/시각 · 집계에 반영된 라운드 목록.
- 클라이언트는 직접 카운트를 올리지 않고 **집계 함수(RPC/Edge Function)만** 호출한다 → 조작·중복 요청 방지.

### 3.3 좌표 변환

- 링 단위 = 미터 × 100 (`ringUnitsPerMeter = 100`).
- 오버뷰 이미지는 게임 추출 이미지와 구도가 픽셀 단위로 같다 (2026-11-16 검증). `constants.ts`의 scale/offset을 그대로 쓴다.

## 4. 같은 경기 중복 제거

같은 경기에 앱 사용자가 여럿이면 같은 링이 여러 번 들어와 히트맵에 점이 튄다.

### 4.1 실측 (2026-11-23, `matches.ring_rounds`, 42경기 · 3개 맵)

| 비교 | 결과 |
|------|------|
| 같은 경기 (스쿼드원끼리 각자 기록) 10쌍 | 공유한 **모든 라운드 좌표가 0.0 단위까지 완전히 일치** |
| 같은 경기의 라운드 시각 차이 (33개 라운드 쌍) | 예고 · 종료 시각 **최대 2.4초** (대부분 0.2~1.5초) |
| 같은 경기의 시작 시각 차이 | 최대 140초 (기록 시점 차이) |
| 다른 경기끼리 첫 라운드 중심 최소 거리 | **587 단위 (~5.9m)**, 2,000 단위 안 3쌍 |

- 첫 라운드 중심은 맵 전체가 아니라 좁은 범위에서 정해지는 것으로 보인다.
- **반올림(예: 50 단위) 지문은 위험.** 위 간격으로 추정하면 맵·시즌당 1만 경기에서 수백~천 건이 잘못 묶일 수 있다.

### 4.2 판정 규칙

같은 경기로 판정하려면 1~3을 **모두** 만족, 또는 4를 만족:

1. 같은 맵 · 시즌, 시작 시각 **±10분** 안.
2. 공유하는 **모든 확정 라운드 좌표가 저장값(0.1 단위) 그대로 일치**. 확정 라운드가 2개 이상이면 2개 이상 일치 필요.
3. 공유하는 모든 라운드의 **예고 · 종료 시각이 ±3초** 안.
4. 두 기록의 킬·다운 이벤트 또는 팀원 목록에 **같은 플레이어 이름**이 있으면 확정 (한 플레이어는 동시에 두 경기에 있을 수 없음). 이름은 함수 안에서 비교만 하고 저장하지 않는다.

### 4.3 동시 진행 중인 다른 경기

- 링이 미리 정해진 목록에서 뽑히는 구조라면 다른 경기에서 좌표가 완전히 같을 수 있다 (42경기 표본에서는 미확인).
- 그래도 묶이려면 두 경기가 **같은 3초 창에서 드롭**하고 모든 공유 라운드 좌표까지 같아야 한다 → 극히 드묾.

### 4.4 오판의 비대칭

| 오판 | 결과 | 통계 영향 |
|------|------|-----------|
| 같은 경기 → 다른 경기로 판단 | 같은 링 2번 카운트 | **튀는 점** (막아야 할 문제) |
| 다른 경기 → 같은 경기로 판단 | 한 경기 누락 | 표본 1개 손실, 분포 왜곡 없음 |

→ 판정은 **같은 경기를 확실히 묶는 쪽(느슨하게)**이 통계적으로 안전하다.

### 4.5 처리 흐름

1. 경기 종료 → 클라이언트가 `(맵, 시즌, 시작 시각, 라운드별 중심·반경·시각)` 전송.
2. 집계 함수가 §4.2로 기존 지문과 대조.
   - 새 경기 → 지문 저장 + 3라운드 이후 라운드 칸 카운트 +1.
   - 기존 경기인데 이번 보고에 **새 라운드가 있음** (일찍 죽은 사용자 → 끝까지 간 사용자) → 새 라운드만 +1.
   - 기존 경기, 새 라운드 없음 → 무시.
3. 판정 결과(특히 "같은 경기인데 시각 차이가 큼")를 로그로 남겨 기준을 재검증.

## 5. 표시

| 히트맵 | 내용 | 용도 |
|--------|------|------|
| **중심 밀도** | 링 중심점 분포 | 링이 주로 어디로 끝나나 |
| **포함 확률** | 링 원 영역 누적 | N라운드에 이 지점이 링 안일 확률 (자리 잡기) |

- 라운드 필터 (3 · 4 · 최종), 라운드별 표본 수 표시 (일찍 죽은 경기는 후반 라운드가 빠지므로).
- 링 위치는 플레이어 행동과 무관 → 여러 사용자 데이터를 합쳐도 분포 왜곡 없음. 개인 히트맵은 표본이 적어 보조로만.
- 랜드마크 이름(§1, 자동 추출)은 위치 참고용 라벨로만 쓴다.

## 6. 착수 전 재검증 (데이터 더 쌓인 뒤)

`matches.ring_rounds` 기준으로 다시 확인:

1. 같은 경기 쌍의 라운드 시각 차이가 여전히 **3초 안**인지 (분포 · 최댓값).
2. 다른 경기에서 링 좌표가 **완전히 같게 반복**된 사례가 있는지 (링 목록 방식 여부).
3. 맵·라운드별 반경 목록 (라운드 판정용, §2.2).
4. 표본 수: 맵 · 시즌 · 라운드별 확정 중심 개수.

2번에서 반복이 발견되면 §4.2를 강화한다 (시간 창 축소, 일치 라운드 수 증가, 이름 교차 필수화).
